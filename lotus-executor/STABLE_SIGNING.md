# Lotus Executor — постоянная подпись APK

## Статус (2026-10-13)
Исходники Android v0.3 собираются. Настоящий ключ подписи **ещё не создан**. На телефоне установлена v0.2, подписанная прежним одноразовым отладочным сертификатом. При переходе на постоянный сертификат потребуется **одна** переустановка; после неё APK с тем же сертификатом и большим `versionCode` будет обновляться поверх.

## Что подготовлено
- `.github/workflows/lotus-executor-stable-release.yml` (зарегистрирован в `main`): вручную запускаемая сборка, которая читает исходники исключительно из ветки `lotus-executor-apk-prototype`. Требует три существующих GitHub Secrets, проверяет настоящий APK Signature Scheme v2 и закреплённый SHA‑256 сертификата. При ошибке APK не публикуется.
- `bootstrap-stable-signing.sh`: выполняется **самим владельцем в доверенном терминале** на Linux, где установлены `keytool` (JDK), `openssl`, `tar`, `base64`, `gh` (GitHub CLI, уже авторизованный владельцем). Никакой `sudo`, SSH и операций Lotus Control.
- Одноразовый CI тест с временным ключом проверяет **только механику** сборки и подписи и уничтожает этот APK. CI-ключ никогда не распространяется как пользовательская версия.

## Однократная подготовка владельцем
В открытом исходнике изучить `bootstrap-stable-signing.sh` и запустить его в доверенном Linux-терминале. Он:
1. Проверяет инструменты и `gh auth status`. Если их нет, ничего не устанавливает и останавливается с понятной ошибкой.
2. Создаёт RSA-3072 PKCS12-ключ с именем `lotus-executor-stable` и случайный пароль в `~/.local/share/lotus-executor-signing/`. Директория и файлы ограничены правами владельца.
3. Повторный запуск **использует старый ключ**, а не генерирует новый. Если в GitHub уже есть секрет ключа, но местная копия пропала, он блокирует создание другого ключа.
4. Через `gh secret set -R latatuev/kids-tv -f` сохраняет в GitHub Secrets зашифрованные значения `LOTUS_EXECUTOR_KEYSTORE_B64`, `LOTUS_EXECUTOR_SIGNING_PASSWORD` и `LOTUS_EXECUTOR_SIGNING_CERT_SHA256`. Ни ключ, ни пароль не коммитятся в репозиторий, чат или документацию.
5. Создаёт `~/lotus-executor-signing-backup.enc` — резервную копию PKCS12 и локального пароля, защищённую отдельным случайным паролем AES-256-CBC/PBKDF2. **Резервный пароль отображается один раз в терминале** и должен быть записан владельцем отдельно. Файл .enc должен быть самостоятельно скопирован на другое устройство или личный Google Drive до установки stable APK.

Важное ограничение: хранение ключа и пароля на одной машине защищено правами ОС, но **не защищает от компрометации учётной записи или диска**. Поэтому отдельная зашифрованная внешняя резервная копия обязательна. GitHub Secrets не является восстанавливаемым бэкапом: его содержимое нельзя прочесть обратно.

## Выпуск
После подтверждённого внешнего резервного копирования ключа:
1. В GitHub Actions запустить `Lotus Executor · Stable signed release` из основной ветки `main`. Workflow автоматически забирает исходники приложения из отдельной ветки `lotus-executor-apk-prototype`.
2. Workflow откажется собирать APK, если хотя бы один секрет отсутствует, сертификат изменился, v2-подпись не проходит или задействована другая ветка.
3. Скачать **только** artifact `lotus-executor-stable-signed`, не `lotus-executor-debug-apk`.
4. Первая установка поверх старой v0.2 не пройдёт из-за сертификата: после одобрения пользователя нужно сохранить нужные данные, удалить **только** старый Lotus Executor v0.2 и установить этот stable release один раз.
5. В следующих версиях повышать `versionCode`, не менять `applicationId=io.lotus.executor` и сертификат. Проверить обновление поверх на тестовом устройстве перед распространением.

## Не делать
- Не создавать новый ключ на каждом запуске CI.
- Не публиковать `.p12`, файл пароля или их base64 в GitHub исходниках, issues, чатах, скриншотах, логах.
- Не использовать `Lotus` защищённые пути, доступ к которым ранее был отклонён. Этот workflow никак не расширяет Control Plane и не обращается к его секретам.
- Не заявлять, что реальная signed APK выпущена или что обновления уже проверены до полноценного запуска release workflow и устройства.

## Что остаётся
1. Выполнить owner-run bootstrap в доверенном окружении с GitHub CLI и Java; сохранить внешнюю копию и резервный пароль.
2. Провести настоящую stable release сборку, проверить certificate hash и APK.
3. Согласовать один переход со старой v0.2, зарегистрировать телефон в уже опубликованном независимом Supabase-приёмнике и проверить реальный подписанный POST.
